# Echo Developer (Echo Alchemist V2 统一开发者)

本 Skill 是 Echo Alchemist V2 项目的统一开发入口。随着项目架构改造（Phase 1-3）的全面完成，所有被分配代码修改任务的 Agent **必须**遵循本工作流，以确保代码质量、架构一致性（特别是事件驱动和组合模式）以及活文档的同步更新。

## 标准工作流 (必须严格遵循)

项目当前已经完成了模块化拆分、事件总线解耦和 `bind` 组合模式的重构。在开发新特性或修复 Bug 时，请严格按照以下步骤进行：

1. **克隆/拉取仓库**
   - 目标仓库：`gdszyy/echo-alchemist-v2-1766564886`
   - 必须在执行任何修改前获取最新代码，确保基于最新架构（如无 Mixin 模式的 `core.js`）进行开发。

2. **读取全局规范与模块索引**
   - 读取仓库根目录下的 `AGENTS.md`。
   - 了解项目的全局开发规范、子模块的职责划分，以及当前项目的架构状态（如 `EventBus` 和 `bind` 组合模式）。

3. **读取模块专属规范**
   - 根据当前任务涉及的模块，读取 `.cursor/rules/` 目录下对应的 `*.md` 规范文件。
   - 例如，修改 UI 相关代码时，必须读取 `.cursor/rules/ui_system.md`；修改战斗逻辑时，需读取 `src/combat/combat.md` 或 `.cursor/rules/events.md`。

4. **执行代码修改**
   - 遵循下文的 **智能编辑策略决策树** 进行代码修改。
   - 确保修改符合已读取的全局和模块规范，特别注意不要破坏已建立的事件驱动架构。

5. **同步更新文档 (关键步骤)**
   - **在同一个 Commit 中**，必须同步更新对应模块的 `.cursor/rules/*.md` 或其他相关架构文档。
   - 确保“活文档”始终反映最新的代码状态。

6. **提交与保存交付物**
   - 提交 Git Commit。
   - 使用 `hub_repo.py save-result` 将修改后的代码文件和文档作为交付物保存到 Git 文档库。

## 智能编辑策略决策树

在修改代码时，请根据修改规模选择最合适的编辑策略，严禁全量交付超过 500 行的文件：

- **微型修改 (< 20 行)**
  - **策略**：使用搜索替换 (Search & Replace) 或行内编辑工具。
  - **适用场景**：变量名重命名、简单的逻辑修复、单行配置修改、事件名称替换。

- **中型修改 (20 - 200 行)**
  - **策略**：使用 Unified Diff 格式进行局部替换，或使用 `edits` 工具进行精准修改。
  - **适用场景**：函数重构、添加新方法、局部逻辑重写、在现有子系统中增加事件监听器。

- **大型修改 (> 200 行)**
  - **策略**：全文件重写 (Full File Rewrite)。
  - **适用场景**：模块整体重构、引入大型新特性。
  - **注意**：仅适用于已拆分的小文件（如 `src/combat/damage_calc.js`）。严禁对 `entities.js` 等大文件执行此策略。

- **脚本化修改 (跨文件/结构性)**
  - **策略**：编写 Python 脚本或复杂的 `sed`/`awk` 脚本进行批量处理。
  - **适用场景**：全局 API 签名变更、大规模文件重命名、统一格式化调整。

## 禁止行为清单

为了维护项目的健康发展，以下行为被**严格禁止**：

1. **禁止全量交付超过 500 行的文件**：对于超大文件（如尚未完全拆解的 `entities.js`），必须进行模块化拆分，或者仅提交 Diff/局部修改。
2. **禁止跳过文档更新步骤**：代码修改必须伴随对应的文档（尤其是 `.cursor/rules/` 下的规范）更新。
3. **禁止在业务模块中直接操作 DOM**：Echo Alchemist V2 已全面引入 `EventBus` 机制，业务逻辑模块必须通过 `eventBus.emit` 派发事件，严禁直接操作 DOM。
4. **禁止使用 Mixin 模式扩展 Game 类**：自 Task 3.3 起，`core.js` 已完全移除 `Object.assign(Game.prototype, ...)`。新增子系统必须遵循组合模式（Composition via bind），严禁再次污染全局原型链。
5. **禁止使用未授权的第三方库**：所有新依赖的引入必须经过协调者或架构师的批准。
6. **禁止在主分支直接开发**：所有任务必须在对应的特性/修复分支上进行。
