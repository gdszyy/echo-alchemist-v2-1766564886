# 决策记录：否决敌人分层渲染（Layered Rendering）方案

**日期**：2026-05-01
**状态**：已否决
**上下文**：Echo Alchemist V2 敌人视觉重构（位图化）

## 1. 背景与目标

在将敌人从矢量绘制升级为位图 Sprite 的过程中，为了解决 9 种基础词缀（包含新增的重装词条）可能产生的 45 种双词缀组合带来的美术工作量爆炸问题，我们提出并测试了**分层渲染（Layered Rendering）**方案。

该方案试图将敌人拆分为三层独立组件：
1. **Base（底盘/腿部）**：决定移动方式（如普通双腿、履带、史莱姆底盘）。
2. **Body（躯干/装甲）**：决定核心防御和攻击特征（如护盾装甲、狂暴核心）。
3. **Attachments（外挂组件）**：决定附加能力（如力场节点、治疗香炉）。

目标是通过代码在运行时将这三层动态拼装，从而用少量组件组合出所有词缀变体。

## 2. MVP 测试过程

我们使用 Nano Banana 生成了护盾词缀（Shield）的四层独立组件（Base、Body、Attachment、Head），并使用 `rembg`（isnet-general-use 模型）进行了透明底抠图。随后，编写 Python 脚本模拟了游戏内的逐层叠加效果。

测试输出了以下结果：
- 各层独立透明底 PNG。
- 逐层叠加过程图（Base → Base+Body → Base+Body+Attach → 完整）。
- 最终在深色战场背景下的合成效果图。

## 3. 否决原因

尽管 MVP 测试在技术管线上跑通了（生成 → 抠图 → 合成），但经过视觉评估和工程可行性分析，我们决定**否决**该方案。主要原因如下：

### 3.1 视觉割裂感与透视问题

分层拼装本质上是 2D 纸娃娃系统（Paper Doll）。在像素艺术（Pixel Art）风格下，不同组件之间的光影、透视和边缘过渡极难自然融合。
- **光影不统一**：各层独立生成时，AI 无法保证全局光照的一致性。躯干的阴影无法正确投射到底盘上。
- **透视错位**：在动态动画（如攻击前倾、受击后仰）中，简单的 2D 坐标偏移无法处理复杂的透视变化，会导致严重的视觉穿帮。

### 3.2 锚点对齐的工程复杂度极高

在 MVP 测试中，我们发现**偏移量（Offset）是核心痛点**。
- 为了让头部、躯干、底盘和外挂组件正确对齐，必须为每一种组件建立极其精确的**锚点坐标系（Anchor Grid）**（如 `waist_y`, `neck_y`, `shoulder_x`）。
- 在 AI 生成管线中，强制要求 AI 严格按照像素级锚点生成图像的成功率极低，需要大量的人工后期修图和坐标微调。
- 考虑到还要支持 idle / move / hit / cast 四行动画帧，锚点对齐的工作量将呈指数级增长，完全违背了降低美术工作量的初衷。

### 3.3 动作动画的僵硬

分层渲染意味着动画只能通过代码控制各层的平移、旋转和缩放（类似 Spine 骨骼动画的低配版）。在像素风格下，这种形变动画会破坏像素的完美对齐（Pixel Perfect），导致画面模糊和边缘锯齿，无法实现传统逐帧动画（Frame-by-Frame）的流畅感和打击感。

## 4. 结论与后续方向

**结论**：分层渲染方案在技术上可行，但在视觉质量和工程维护成本上不可接受，予以否决。

**后续方向**：
放弃物理组件的硬拼装，转向**视觉特征融合**与**特效叠加**的混合方案：
1. **基础 Sprite 降维**：不再为 45 种组合生成独立 Sprite。只为 9 种单词缀生成高质量的完整 Sprite（包含完整动画帧）。
2. **双词缀处理**：当出现双词缀（如 Shield + HeavyArmor）时，选择其中**视觉特征更强**的一个作为主 Sprite（Base Sprite）。
3. **特效层补偿**：另一个词缀的特征通过现有的动态特效层（Layer 3.5 内部特效、Layer 1.6 色调叠加、Layer 3.6 印章）来体现。例如，使用 HeavyArmor 的 Sprite，同时叠加 Shield 的蓝色色调和力场网格特效。

这种方案既能保证基础 Sprite 的视觉完整性和动画流畅度，又能复用现有的特效系统，将美术工作量控制在 9 套 Sprite 以内。
